第 8 课 · 主干道（下）：implement——四行字串起全部内功

阶段 3 · 工作流主干道 ｜ 预计 10 分钟 ｜ 使命：驾驭 AI Agent 的工程内功

本课只教一件事 implement/SKILL.md 是全套 skills 里"编排的极致"：正文四句话，却串起了你学过的全部内功。本课一半讲它，一半带你俯瞰整条主干道——这是收官前的全景图。

一、一手源码全文（真的只有四句）

Implement the work described by the user in the spec or tickets.

Use /tdd where possible, at pre-agreed seams.

Run typechecking regularly, single test files regularly,
and the full test suite once at the end.

Once done, use /code-review to review the work.

Commit your work to the current branch.
中文对照

① 实现用户在规格或票据中描述的工作。

② 尽可能使用 /tdd，在预先约定的接缝上。

③ 频繁跑类型检查、频繁跑单个测试文件，最后完整跑一次全量测试套件。

④ 完成后，用 /code-review 审查工作。

⑤ 把工作提交到当前分支。

二、逐句看它调用了你学过的什么

句调用的内功出自哪课
"in the spec or tickets"输入必须是 to-spec / to-tickets 的产物——没有规格不开工第 7 课
"Use /tdd... at pre-agreed seams"红绿循环 + 预先约定的接缝（两道行动闸门一次引用）第 4、6 课
"typecheck regularly... full suite once at the end"反馈循环的节奏设计：便宜的反馈（类型检查、单文件测试）高频跑，昂贵的反馈（全量套件）只在最后跑一次第 1 课（反馈速率 = 速度上限）
"use /code-review"双轴审查 + 12 坏味道基线；TDD 循环里欠下的重构债在这里还第 5、6 课
"Commit to the current branch"明确的完成标准（第 2 课）——落点清晰，不多不少第 2 课

四句话零新概念——所有的"厚"都住在被调用的 skill 里。implement 本身就是一个深模组：接口小（四句话），行为大（整条实现纪律）。Matt 把第 4 课的理论用在了 skill 的组织上，第三次了（grill-me、grill-with-docs、implement）。

再看一眼 Matt 与大框架的分野：这条主干道每一站都可以独立进出——手里已有规格（主管给的、别的 AI 产的），直接从 to-tickets 上道；只想拷问不想开发，grill-me 用完就走。这就是 README 里那句"从哪步开始、哪步结束完全由你决定"。

四、随堂测验

Q1 · implement 为什么规定"类型检查频繁跑、全量测试套件只在最后跑一次"？

✅ 正确。反馈循环的经济学：类型检查和单文件测试秒级出结果——高频跑，让 agent 始终贴着反馈面工作；全量套件分钟级——只在最后收口跑一次，确认无回归。对照第 1 课引言："The rate of feedback is your speed limit."（反馈速率就是你的速度上限。）这套节奏值得原样搬进你自己 Agent 的执行循环。
关键词：反馈的成本分层。便宜的反馈（typecheck、单文件测试，秒级）高频跑；昂贵的反馈（全量套件，分钟级）最后跑一次收口。既保住"反馈速率 = 速度上限"（第 1 课），又不为反馈本身付出过量时间。

Q2 · "implement 本身就是一个深模组"——这个说法的依据是什么？

✅ 正确。按第 4 课定义：深度 = 接口的杠杆。你（调用者）只需学会一句 /implement，就撬动了 TDD 纪律 + 反馈节奏 + 双轴审查 + 提交规范的完整行为链——小接口，大行为。而这些行为的"实现"分散在 tdd、code-review 等被编排的 skill 里（内部零件），不暴露给调用者。
用第 4 课的尺子量：深度是接口的属性。implement 的接口 = 四句话（学习成本极低），撬动的行为 = 整条实现纪律（TDD + 反馈节奏 + 审查 + 提交）。小接口 + 大行为 = 深模组。前两个选项都在拿"实现侧"或"使用侧"的属性说事，和深度定义无关。

Q3 · 你手里已经有一份主管写好的详细 PRD，想直接开始拆任务。按 Matt 的主干道哲学，正确做法是——

✅ 正确。README 原话：手上有份规格（自己写的/主管给的/别的 AI 产的）就能直接跳到 to-tickets。每站独立进出正是与 Superpowers 式"绑死九步"的核心区别。（直接 implement 则跳过头了：没有垂直切片和阻塞边，一整份 PRD 塞不进一个 context window——第 7 课 Q2 的约束还在。）
"小而模组化"的红利就在这：每站可独立进出，有规格就从 to-tickets 上道，不必重走上游（重新拷问/重写规格是在给流程上枷锁——Matt 批评大框架的正是这个）。但也别跳过 to-tickets 直接 implement：整份 PRD 塞不进一个 context window，垂直切片和阻塞边是并行与保绿的前提。
本课小胜利 主干道全线贯通。你现在能把任何一个模糊想法，沿着"拷问 → 规格 → 票据 → 实现 → 审查"走成可交付的代码——并且知道每一站背后的纪律为什么长那样。
