第 6 课 · TDD：防作弊的红绿循环

阶段 2 · 工程内功 ｜ 预计 15 分钟 ｜ 使命：驾驭 AI Agent 的工程内功

本课只教一件事 tdd/SKILL.md 不只是"先写测试"——它回答了三个更难的问题： 什么样的测试值得写（读起来像规格）、测试写在哪（预先约定的接缝）、什么顺序写（垂直切片，每次一发曳光弹）。 防御目标：失控模式三（代码跑不起来 / AI 拿假测试交差）。

一、好测试的唯一标准：像一份规格

"Tests verify behavior through public interfaces, not implementation details. Code can change entirely; tests shouldn't. A good test reads like a specification."
（中文：测试通过公共接口验证行为，而不是实现细节。代码可以整个重写，测试不应该跟着变。好的测试读起来像一份规格说明。）

例子：测试名 "user can checkout with valid cart"（用户可以用有效购物车结账）——一眼看出系统有什么能力，重构内部实现也不会碎，因为它根本不关心内部结构。

二、测试写在哪：预先约定的接缝

第 4 课的 Seam（接缝）在这里兑现了第二个用途：

"Test only at pre-agreed seams. Before writing any test, write down the seams under test and confirm them with the user."
（中文：只在预先约定的接缝上测试。写任何测试之前，先写下要测的接缝清单，并与用户确认。）

为什么要"预先约定"？——你不可能测完所有东西。先约定接缝，测试火力才会集中到关键路径和复杂逻辑上，而不是平均撒到每个边角。注意这又是一道"行动闸门"（第 2 课）：AI 必须先问"公共接口是什么、测哪些接缝？"拿到人类确认才能动笔。

三、三大反模式（AI 写测试的高发病）

反模式症状识别信号
Implementation-coupled
实现耦合		 mock 内部协作者、测私有方法、从旁路验证（比如绕过接口直接查数据库） 行为没变、只是重构了一下，测试就碎了
Tautological
同义反复		 断言用和被测代码同样的方式重新算一遍期望值：expect(add(a,b)).toBe(a+b)——恒真，永远不可能不同意代码 期望值不是来自独立的真相来源（已知正确的字面量、手工算例、规格）
Horizontal slicing
水平切片		 先把所有测试一口气写完，再写所有实现——批量测试验证的是想象中的行为 测的是"东西的形状"而不是用户可见的行为；在理解实现之前就锁死了测试结构
第 2 站的伏笔在这里收线 第 1 课说"AI 是作弊仔，会拿错误实现配必然通过的假测试"。现在你有了精确的病名：那就是 Tautological（同义反复）测试——期望值和实现出自同一套逻辑，同错同绿。 解药也精确了：期望值必须来自独立的真相来源（Expected values must come from an independent source of truth）+ 先红后绿（测试必须先失败过，证明它有能力不同意代码）。

四、循环的三条规则

  1. Red before green（先红后绿）：先写会失败的测试，然后只写刚好够通过的代码——不预支未来的测试，不加投机功能（联动第 5 课 Speculative Generality）
  2. One slice at a time（一次一片）：一个接缝、一个测试、一次最小实现。垂直切片，每个测试是一发tracer bullet（曳光弹）——根据上一轮学到的东西调整下一发的弹道
  3. Refactoring is not part of the loop（重构不在循环内）：重构属于审查阶段（code-review skill 的事）——红绿循环里只做红→绿，不顺手"优化"

另一个细节：探索代码库时先读 CONTEXT.md（第 3 课的共享语言），让测试名使用领域词汇——测试就成了领域规格的可执行版本。skills 之间的咬合又出现了。

五、随堂测验

Q1 · AI 写了这个测试：expect(calcDiscount(cart)).toBe(cart.total * 0.9)，而实现正是 return cart.total * 0.9。这是哪种反模式？

✅ 正确。断言用和实现相同的公式重新算期望值——如果公式本身错了（比如该打 8 折写成 9 折），测试照样绿。修复：期望值来自独立来源，比如手工算例：购物车 100 元 → 断言 toBe(90)（一个已知正确的字面量）。
看断言的来源：cart.total * 0.9——和实现是同一个公式。公式错了测试也绿，恒真式，这就是 Tautological（同义反复）。解药：期望值必须来自独立真相来源——手工算好"100 元的购物车应得 90"，断言写死 toBe(90)。

Q2 · 重构了模块内部结构（行为完全没变），结果 8 个测试全碎了。按本课诊断，这批测试的病是——

✅ 正确。源码给的识别信号一字不差："The tell: the test breaks when you refactor but behavior hasn't changed."（信号：重构后行为没变，测试却碎了。）好测试只依赖公共接口——"代码可以整个重写，测试不应该跟着变"。最后一个选项是流传最广的错误直觉。
源码的识别信号："the test breaks when you refactor but behavior hasn't changed"（行为没变、重构就碎）= Implementation-coupled（实现耦合）。好测试穿过公共接口验证行为，内部怎么重写都不碎。"重构后更新测试是正常的"恰恰是这个反模式最舒适的伪装。

Q3 · 为什么"先把 20 个测试全写完，再开始写实现"是反模式，明明也是"测试先行"？

✅ 正确。这是 Horizontal slicing（水平切片）："Bulk tests verify imagined behavior"（批量测试验证的是想象中的行为）——在理解实现之前就锁死测试结构，测的是形状不是行为。正确姿势：垂直切片，一测试→一实现→循环，每发曳光弹根据上一发的落点修正。（最后一个选项有迷惑性：技术上每个测试仍可以先红后绿，问题不在红绿，在"提前锁死"。）
TDD ≠ "测试先行"就够了。一口气写 20 个测试 = Horizontal slicing：那 20 个测试验证的是你想象中的行为，在理解实现之前就锁死了测试结构。正确姿势是垂直切片：一个测试→一次实现→根据学到的调整下一个测试（曳光弹）。

Q4 · 红绿循环进行中，AI 发现刚写完的函数命名不佳、还有一段重复代码，提议"顺手重构一下"。按循环规则，正确做法是——

✅ 正确。源码第三条规则："Refactoring is not part of the loop. It belongs to the review stage."（重构不属于循环，它属于审查阶段。）红绿循环只做红→绿，重构留给 code-review（第 5 课的双轴审查会抓住 Mysterious Name 和 Duplicated Code）。职责分离，每个阶段只干一件事——"顺手"是纪律的天敌。
循环规则第三条原文："Refactoring is not part of the loop. It belongs to the review stage (see the code-review skill)."——红绿循环内只做红→绿；命名和重复代码的问题留给审查阶段（第 5 课的 Mysterious Name、Duplicated Code 正是为此待命）。阶段纪律的意义：每个阶段一件事，"顺手"会让循环失焦。
本课小胜利 三个反模式名字（实现耦合 / 同义反复 / 水平切片）+ 一条金标准（期望值来自独立真相来源）。 下次让 AI 写测试，验收清单就是这四条。
