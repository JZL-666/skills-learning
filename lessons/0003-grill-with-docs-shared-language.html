第 3 课 · 拷问的进化：grill-with-docs 与共享语言

阶段 1 · 拷问的艺术 ｜ 预计 12 分钟 ｜ 使命：驾驭 AI Agent 的工程内功

本课只教一件事 grill-me 的罩门是失忆：会话一关，吵出来的共识全部蒸发。grill-with-docs 的解法是让拷问顺手留下两种文档——共享语言（CONTEXT.md）和决策记录（ADR）。这一课同时防御失控模式一（未对齐）和模式二（啰嗦）。

一、一手源码：还是一行编排

grill-with-docs/SKILL.md 的完整正文：

Run a `/grilling` session, using the `/domain-modeling` skill.

（中文：运行一场 /grilling 拷问会话，同时使用 /domain-modeling 领域建模技能。）

第 2 课的 Wrapper 模式再次出现，但这次是组合两个引擎：

grill-me        =  grilling（拷问引擎）
grill-with-docs =  grilling（拷问引擎）+ domain-modeling（建模引擎）

Matt 自己更常用 grill-with-docs。真正的新知识全在 domain-modeling/SKILL.md 里——这是本套 skills 中少见的"长 skill"（75 行），因为它承载的是一门完整学科的压缩：DDD（领域驱动设计）。

二、domain-modeling 的五个"会话中动作"

拷问进行时，AI 被要求随时执行这五个动作（每条都引自源码，附中文）：

#动作源码原文（英）中文对照 + 它在防什么
1 用术语表对质 "Your glossary defines 'cancellation' as X, but you seem to mean Y — which is it?" "你的术语表把'取消'定义为 X，但你现在说的像是 Y——到底是哪个？"
防：同一个词悄悄变味，代码和讨论渐行渐远
2 锐化模糊用词 "You're saying 'account' — do you mean the Customer or the User?" "你说'账户'——你指的是客户（Customer）还是用户（User）？这是两回事。"
防：一词多义在系统里埋雷
3 用具体场景压力测试 "Invent scenarios that probe edge cases and force the user to be precise" 发明探测边界的场景，逼用户对概念边界给出精确回答
防：概念关系只在"理想情况"下成立
4 和代码交叉验证 "Your code cancels entire Orders, but you just said partial cancellation is possible — which is right?" "你的代码只能整单取消，但你刚说可以部分取消——哪个对？"
防：嘴上的模型和代码里的模型分裂
5 当场写入 CONTEXT.md "When a term is resolved, update CONTEXT.md right there. Don't batch these up" 术语一敲定就立刻写入，不要攒着批量处理
防：会话结束共识蒸发（grill-me 的罩门）
Agent 工程师视角 CONTEXT.md 对 AI 的本质是什么？——一份人工维护的"语义压缩词表"。 README 举的例子：没有它，要说"当课程章节里的某节课被'落实'（即在文件系统中获得位置）时出了问题"； 有了它，一个词："materialization cascade（落实级联）出了问题"。 这就是你设计自己 Agent 时的启示：给 Agent 一份领域词表，token 消耗、命名一致性、导航效率三线齐收。 这也正是失控模式二（啰嗦）的根治法——不是叫 AI"说话简洁点"，而是给它一门更高压缩比的语言。

三、CONTEXT.md 的格式纪律（三条最容易踩的）

源码 CONTEXT-FORMAT.md 的词条格式长这样：

**Invoice**:
A request for payment sent to a customer after delivery.
_Avoid_: Bill, payment request

（中文：发票（Invoice）：交付后向客户发出的付款请求。避免使用：Bill、payment request。）

  • 要有立场（Be opinionated）：多个词指同一概念时，选定一个最佳词，其余全打入 _Avoid_ 黑名单——这不是宽容的同义词典，是独裁的标准语
  • 只收本项目特有概念：超时、错误类型这类通用编程概念不配入表——问自己"这是本领域独有的概念，还是通用编程概念？"
  • 纯词汇表，零实现细节：源码原话 "It is a glossary and nothing else"（它是术语表，仅此而已）——防止它腐化成规格书或草稿纸（想想第 2 站 to-spec 为什么禁止代码入 spec，同一个道理：越稳定的文档越不能掺易变的内容）

四、ADR：三个条件缺一不写

ADR（Architecture Decision Record，架构决策记录）回答的是"当初为什么这么干"。domain-modeling 刻意要求克制（offer ADRs sparingly，谨慎提议），三条件全满足才写：

条件原文中文
1Hard to reverse难以回头——将来反悔的代价是实打实的
2Surprising without context缺了上下文会让人惊讶——未来读者会问"当初为什么这样搞？"
3The result of a real trade-off真实取舍的产物——当时确有多个选项，你为了特定理由选了这个

缺任何一条都跳过。为什么要克制？——回忆 writing-great-skills 的"修剪"原则：文档和 prompt 一样，多一份废文档，未来读者（人和 AI）就多一分分心。

五、随堂测验

Q1 · 拷问中你说"用户下单后账户会扣款"，AI 回应："你说的'账户'，是指术语表里的 Customer 还是支付上下文里的 Wallet？"这是五个动作中的哪一个？

✅ 正确。"账户"是一词多义（overloaded term），AI 提议在两个候选精确概念中二选一——这是"锐化模糊用词"。（如果术语表已有定义而你用歪了，那才是动作一。）
注意区分：动作一的前提是术语表里已有定义而你的用法和它冲突；这里"账户"根本没入表，只是一词多义需要拆开——属于动作二"锐化模糊用词"。

Q2 · 团队想把"我们选了 PostgreSQL 而不是 MongoDB，因为需要事务保证"写成文档。按三条件判断，该写成什么？

✅ 正确。换数据库代价巨大（难回头）、未来的人会问为什么不用更时髦的方案（缺上下文会惊讶）、确实在两个真实选项间做了取舍——三条全中，写 ADR。注意它不能进 CONTEXT.md：那是纯术语表，零实现细节。
逐条过：难回头？换数据库伤筋动骨，✓。缺上下文会惊讶？未来读者会问"为什么不用 X"，✓。真实取舍？Postgres vs Mongo 是真选择，✓。三条全中 → 写 ADR。CONTEXT.md 不行——它是纯术语表（"a glossary and nothing else"）。

Q3 · 为什么 CONTEXT.md 严禁写实现细节？（提示：回忆 to-spec 禁止在规格书里写代码的理由）

✅ 正确。这是整套 skills 反复出现的深层原则：按变化频率分层——术语和"要解决什么问题"最稳定，代码最易变。把易变的掺进稳定的，稳定文档就会过期说谎，AI 下次读到过期内容会被带偏，越改越乱。
核心是变化频率：代码天天变，术语很少变。混入实现细节后，代码一改文档就过期，下次 AI 拿着过期文档干活会被带偏——和 to-spec 禁代码是同一条深层原则：按变化频率给文档分层。

六、课后

  • 主要阅读（一手，10 分钟）：domain-modeling/SKILL.md 全文 + Matt 真实项目的 CONTEXT.md 实例（看看真家伙长什么样）。
  • 可选加分项（不阻塞）：哪天你在公司项目里跑一次 grill-with-docs，把生成的 CONTEXT.md 拿去让你的 AI 老师点评（结合 domain-modeling/SKILL.md 做对照）。
  • 深入路径：DDD 的水很深，本课只取了 skills 用到的那瓢。如果想深入某个概念，可以打开你的 AI coding Agent，让它结合 domain-modeling/SKILL.md 为你讲解；更系统的参考是 Eric Evans 原文《Domain-Driven Design》。
