第 4 课 · 深模组：一扇小门，一栋大房子

阶段 2 · 工程内功 ｜ 预计 15 分钟 ｜ 使命：驾驭 AI Agent 的工程内功

本课只教一件事 深度（Depth）是接口的属性，不是实现的属性。 搞懂这一句 + 会用"删除测试"，你就掌握了防御失控模式四（泥球化）的核心武器。 本课教材：codebase-design/SKILL.md（源自 Ousterhout《A Philosophy of Software Design》，但 Matt 做了一处重要修正，见第四节）。

一、深 vs 浅：源码里的两张图

深模组（追求）                      浅模组（避免）
┌─────────────────┐        ┌───────────────────────────────┐
│  Small Interface │        │        Large Interface        │
│  小接口：方法少、参数简单  │        │  大接口：方法多、参数复杂        │
├─────────────────┤        ├───────────────────────────────┤
│                 │        │  Thin Implementation          │
│  Deep           │        │  薄实现：只是层层转发            │
│  Implementation │        └───────────────────────────────┘
│  深实现：复杂逻辑全部藏在门后 │
│                 │
└─────────────────┘

源码给出的定义（英中对照）：

"A module is deep when a large amount of behaviour sits behind a small interface, shallow when the interface is nearly as complex as the implementation."
（中文：当大量行为藏在一个小接口背后时，模组是深的；当接口几乎和实现一样复杂时，模组是浅的。）

设计接口时问自己三个问题（源码原文直译）：能不能减少方法数？能不能简化参数？能不能把更多复杂度藏进去？

二、六个必须精确使用的词

这个 skill 的本质是一份设计讨论专用的 CONTEXT.md（第 3 课的共享语言，用在了设计领域）。源码开头就警告："Use these terms exactly — don't substitute"（精确使用这些词——不许用别的词代替），连 _Avoid_ 黑名单都配好了：

术语定义黑名单（_Avoid_）
Module 模组任何"有接口 + 有实现"的东西——刻意不限尺寸：函数、类、包都算unit、component、service
Interface 接口调用者要正确使用模组必须知道的一切：类型签名 + 不变式 + 调用顺序约束 + 错误模式 + 性能特征API、signature（太窄，只指类型层面）
Seam 接缝接口所在的位置——"在哪开门"和"门后藏什么"是两个独立的设计决策（术语来自 Michael Feathers）boundary（和 DDD 的 bounded context 撞名）
Adapter 适配器在某个接缝处满足接口的具体实现——描述的是角色（填哪个槽），不是内容物——
Leverage 杠杆深度给调用者的回报：学一份小接口，撬动一大堆能力；一份实现在 N 个调用点 + M 个测试里反复回本——
Locality 局部性深度给维护者的回报：变更、bug、知识、验证都集中在一处——修一次，处处生效——
Agent 工程师视角 Locality（局部性）正是第 1 课那个论断的技术根据：AI 的 context window 有限。 浅模组逼 AI 在十几个文件间跳转拼凑逻辑，超出记忆范围就开始瞎猜； 深模组把来龙去脉集中在一个视野里，AI 可以精准打击。 深模组不只是给人类的架构美学——它是 AI 时代的性能优化。 同样的道理也适用于你设计的 Agent：给它的工具（tool）接口越小越深，Agent 的调用决策就越不容易出错。

三、删除测试（The Deletion Test）——判断深浅的一把刀

"Imagine deleting the module. If complexity vanishes, it was a pass-through. If complexity reappears across N callers, it was earning its keep."
（中文：想象把这个模组直接删掉。如果复杂度消失了，它本来就只是个二传手；如果复杂度在 N 个调用方身上重新长出来，说明它一直在干实事。）

这就是视频笔记里 improve-codebase-architecture 做"架构大扫除"用的那把刀。两个走向：

  • 删掉后天下大乱、隐藏的复杂逻辑全炸回调用方 → 深模组，留下
  • 删掉后代码反而清爽、原本跳两个文件的现在集中一处 → 假装做事的空壳，清理

四、三条容易记错的原则（含 Matt 对经典的修正）

  1. 深度是接口的属性，不是实现的属性。深模组内部完全可以由小的、可替换的零件组成——只要它们不暴露在接口上。模组可以有内部接缝（自己的测试用）+ 外部接缝（接口所在处）。
  2. 一个适配器 = 假想的接缝；两个适配器 = 真实的接缝。原文："Don't introduce a seam unless something actually varies across it."（中文：除非真的有东西会在这条缝两侧变化，否则别引入接缝。）——这是对"为了架构而架构"的当头一棒：只有一个实现却抽了三层接口，就是在给 AI 和人类同时增加导航成本。注意：测试用的内存 fake 也算一个货真价实的适配器。
  3. Matt 对 Ousterhout 的修正——源码"Rejected framings（被否决的定义）"一节明确拒绝了原著"深度 = 实现行数 ÷ 接口行数"的定义，理由："rewards padding the implementation"（中文：这会奖励往实现里灌水）。Matt 改用深度 = 杠杆：每学一单位接口，能换到多少行为。这提醒你：读经典也要带脑子，连大神都在修正大神。

五、为可测试性而设计（两条签名级规则）

// 规则一：接受依赖，不要自己制造依赖
function processOrder(order, paymentGateway) {}   // ✅ 可测试（网关可注入假的）
function processOrder(order) {
  const gateway = new StripeGateway();            // ❌ 难测试（写死了真网关）
}

// 规则二：返回结果，不要制造副作用
function calculateDiscount(cart): Discount {}     // ✅ 可测试（看返回值即可断言）
function applyDiscount(cart): void {
  cart.total -= discount;                         // ❌ 难测试（要检查被改的对象）
}

再加第三条：接口面积小——方法越少，要写的测试越少；参数越少，测试搭台越简单。三条合起来：接口就是测试面（The interface is the test surface）——如果你想绕过接口去测内部，模组八成是长错形状了。

六、随堂测验

Q1 · 代码库里有个 UserService，它的 7 个方法全都是原样转发给 UserRepository 的同名方法（参数不变、无附加逻辑）。用删除测试判断，它是——

✅ 正确。删除测试：删掉它，复杂度没有炸回调用方（调用方只是改叫 userRepository.xxx()，代码反而少一层）——它没隐藏任何东西，是纯二传手。注意最后一个选项的陷阱："为了分层而保留"正是"一个适配器 = 假想接缝"批判的行为。
用删除测试走一遍：删掉 UserService，调用方直接调 UserRepository，参数一模一样，没有任何复杂度重新长出来——复杂度"消失"了，说明它是 pass-through（二传手）。方法多不等于深："7 个方法"是接口大，接口大而实现薄恰恰是浅模组的定义。

Q2 · 某模组内部由 12 个小类组成，互相之间还有依赖注入，但对外只暴露一个 processCheckout(cart) 函数。按本课定义，这个模组——

✅ 正确。原则一：深度是接口的属性。调用者只需学 1 个函数就撬动整个结账流程（杠杆极高）——内部 12 个小类是"内部接缝"，不暴露就不算接口复杂度。第三个选项是陷阱：数行数正是被 Matt 否决的 Ousterhout 式定义（"奖励灌水"）。
关键：深度是接口的属性，不是实现的属性。对外只有 1 个函数 = 小接口；藏着 12 个类的协作 = 大量行为。小接口 + 大行为 = 深模组。内部零件多不但无罪，源码还明确说深模组内部就该可以由小的可替换零件组成（内部接缝）。数行数则是被"Rejected framings"否决的定义。

Q3 · 项目只用 PostgreSQL，短期没有换库计划，测试也直接连测试数据库（不用内存 fake）。同事提议："先抽一个 IDatabase 接口层，万一以后要换呢？"按源码原则，正确回应是——

✅ 正确。"One adapter means a hypothetical seam."（一个适配器 = 假想接缝。）现在只有 Postgres 一个适配器，测试也不经这条缝替换——没有任何东西 varies（变化），引入接缝只会白付导航成本。注意最后一个选项过度了：如果哪天引入内存 fake 跑测试，那就是货真价实的第二个适配器，接缝立刻转正。
源码原话："Don't introduce a seam unless something actually varies across it."（除非真有东西在缝两侧变化，否则别引入接缝。）现在只有一个适配器（Postgres），测试也不替换——缝是假想的。但也别走到"永远不抽"的极端：一旦出现第二个适配器（比如测试用内存 fake），接缝就是真实的了。

Q4 · 下面哪个函数签名同时符合"可测试性"两条规则（接受依赖 + 返回结果）？

✅ 正确。依赖（taxRules）从参数进来（规则一），结果（Invoice）从返回值出去（规则二）——测试时喂假税率、断言返回值，不需要 mock 任何副作用。第二个选项只满足规则一（mailer 注入了，但返回 void、靠副作用干活）；第四个只满足规则二（有返回值，但依赖是偷偷从全局拿的）。
逐一体检：选项一两条全违反（自造依赖 + 副作用）；选项二只过规则一（依赖注入✓，但 void + 副作用✗）；选项四只过规则二（返回结果✓，但全局配置是隐藏依赖✗）。只有 renderInvoice(order, taxRules): Invoice 两条全过：依赖走参数，结果走返回值。
本课小胜利 你现在有了一把随身携带的刀（删除测试）和一句心法（深度是接口的属性）。 下次看任何代码——包括 AI 刚生成的——先问：这个模组删掉会怎样？
