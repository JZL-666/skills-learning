第 5 课 · 12 种代码坏味道与双轴审查

阶段 2 · 工程内功 ｜ 预计 15 分钟 ｜ 使命：驾驭 AI Agent 的工程内功

本课只教一件事 code-review/SKILL.md 的两件武器： 双轴审查（Standards 标准轴 ✕ Spec 规格轴，平行子代理互不污染）+ 12 种坏味道基线（全部出自 Fowler《重构》第 3 章）。 坏味道的价值在于：它们是指引词——一个词顶一百字的解释（第 2 课"给理由"、第 9 课"leading words"的同宗）。

一、双轴审查：为什么要拆成两个平行子代理？

审查 diff 时沿两条独立的轴：

轴问题失败示例
Standards 标准轴代码符合本仓库的成文规范 + 坏味道基线吗？实现了正确的功能，但破坏了项目惯例
Spec 规格轴代码忠实实现了源头 issue/PRD 的要求吗？每条规范都守了，但做的根本不是要的东西
"Both axes run as parallel sub-agents so they don't pollute each other's context... Reporting them separately stops one axis from masking the other."
（中文：两条轴作为平行子代理运行，避免互相污染上下文……分开报告，防止一条轴掩盖另一条轴的问题。）

三个设计细节值得你抄进自己的 Agent：

  • 先验证再开工：进入子代理前先确认 git 引用能解析、diff 非空——"A bad ref or empty diff should fail here — not inside two parallel sub-agents."（坏引用应该在这里失败，而不是在两个平行子代理内部失败。）失败要发生在最便宜的位置
  • 仓库规范 > 基线：项目成文规范永远压过坏味道基线；工具（linter）已强制的东西直接跳过——不重复劳动
  • 坏味道永远是"判断题"：报告写"possible Feature Envy（疑似依恋情结）"，never a hard violation（绝不当硬性违规）——给人留拍板权，熟悉吗？这是 grilling 的"决策归人类"在审查场景的重演

二、12 种坏味道基线（每条：是什么 → 怎么治）

全部译自源码，出处均为 Fowler《Refactoring》第 3 章：

坏味道是什么怎么治
Mysterious Name
神秘命名		函数/变量/类型的名字看不出它是干嘛的重命名；如果起不出诚实的名字，说明设计本身就是浑的
Duplicated Code
重复代码		同一逻辑形状出现在多处提取共享形状，两边都调用它
Feature Envy
依恋情结		方法伸手够别的对象的数据多过用自己的把方法搬到它所依恋的数据那边去
Data Clumps
数据泥团		同样几个字段/参数总是结伴出行（一个想要出生的类型）捆成一个类型，传它
Primitive Obsession
基础类型偏执		用裸的 string/number 硬扛一个值得拥有自己类型的领域概念给这个概念一个自己的小类型
Repeated Switches
重复的分支		对同一类型的同一套 switch/if 级联在多处反复出现换多态，或两处共享一个映射表
Shotgun Surgery
散弹枪手术		一个逻辑变更迫使你在很多文件里到处改把一起变化的东西收拢进一个模组
Divergent Change
发散式变化		一个文件/模组因为几个互不相关的原因被修改拆开，让每个模组只为一个原因而变
Speculative Generality
投机通用性		为规格里没有的需求预加的抽象、参数、钩子删掉；内联回去，等真需求出现再说
Message Chains
消息链		调用方依赖 a.b().c().d() 式的长导航把这段行走藏进第一个对象的一个方法里
Middle Man
中间人		一个类/函数基本只是往下转发砍掉它，直接调真正的目标
Refused Bequest
拒绝的遗产		子类无视或覆盖了它继承来的大部分东西放弃继承，改用组合
你已亲手抓过的 + 和第 4 课的接线 Shotgun Surgery 你抓过活的：导航系统重构那次，"每新增一课就要回改所有旧课"就是它，解法（收敛到 toc-data.js 单一数据源）正是"把一起变化的东西收拢一处"。
再看三个熟脸：Middle Man = 第 4 课删除测试删掉后天下太平的那种浅模组；Speculative Generality = "一个适配器的假想接缝"；Data Clumps / Primitive Obsession = 接口参数没设计好——坏味道清单和深模组理论是同一枚硬币的两面：坏味道是症状，深模组是处方。

三、随堂测验

Q1 · 你的代码里，createUser(name, email, phone)、updateContact(name, email, phone)、sendWelcome(name, email, phone)——这三个参数总是结伴出现。这是哪种坏味道，怎么治？

✅ 正确。"同样几个参数总是结伴出行"就是 Data Clumps——源码的诊断词很形象："a type wanting to be born"（一个想要出生的类型）。接生它：定义 Contact { name, email, phone }，三个函数都改收一个 Contact。
注意症状：不是"同一段逻辑出现多次"（那是重复代码），而是"同一组参数总是结伴旅行"——这是 Data Clumps（数据泥团），治法是把它们捆成一个类型（Contact）。源码的说法："a type wanting to be born"（一个想要出生的类型）。

Q2 · AI 在实现"导出 CSV"需求时，顺手设计了一个 ExportStrategy 接口 + 工厂，"方便以后支持 PDF、Excel"。但规格里只要求 CSV。这是哪种坏味道？

✅ 正确。Speculative Generality——"为规格没有的需求预加的抽象"。治法就一个字：删。这是 AI 生成代码最高发的坏味道之一（AI 特别爱"体贴地"预留扩展点），也是双轴审查里 Spec 轴的"scope creep（范围蔓延）"和 Standards 轴的坏味道少见的双杀。
关键证据："方便以后支持"——为还不存在的需求预加的抽象层，这是 Speculative Generality（投机通用性）。联动第 4 课：这就是"一个适配器 = 假想接缝"的坏味道版本。治法：删掉，等真需求（第二个适配器）出现再抽。

Q3 · 为什么坏味道基线在报告里永远写成"疑似（possible）"，而成文仓库规范的违反可以是"硬性（hard）"？

✅ 正确。源码原文："Each smell is a labelled heuristic, never a hard violation."（每种坏味道是一个带标签的启发式，绝不是硬性违规。）坏味道依赖上下文判断（比如仓库规范明确允许的写法要压过基线），最终裁决权在人——又是那条贯穿全套 skills 的主线：AI 给选项，人类拍板。
源码给的理由是性质而非能力："Each smell is a labelled heuristic（启发式）, never a hard violation"——坏味道天生依赖上下文（仓库规范可以合法压过基线），所以只能标记"疑似"，由人拍板。这是"决策权留给人类"主线在审查场景的体现。

Q4 · 一次改动"给订单加个折扣字段"，diff 显示同一个 utils.ts 这个月已第 4 次因完全不相关的原因（上次是邮件模板、上上次是日期格式）被修改。这是哪种坏味道？

✅ 正确。注意它和散弹枪手术是镜像：Divergent Change = 一个文件被 N 个原因改（万能 utils 是重灾区）；Shotgun Surgery = 一个原因要改 N 个文件。方向相反，病根相同：变化的东西没有按"一起变"的原则归位。治法：拆开 utils，让每个模组只为一个原因而变。
分清镜像对：一个文件因 N 个不相关原因被反复改 = Divergent Change（发散式变化，万能 utils.ts 是重灾区）；一个原因要改 N 个文件 = Shotgun Surgery（散弹枪手术，你抓过的那只）。本题是前者。
本课小胜利 12 个指引词入库。下次审 AI 生成的代码，不用说"总觉得哪里不对"——直接点名："这里疑似 Speculative Generality，删掉。"一个词，AI 秒懂，因为这些词深植在它的训练数据里。
